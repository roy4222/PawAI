## Required investigation

- YOLO26 全家族規格：n/s/m 的 params、GFLOPs、COCO mAP、是否有 `-seg` 變體與其輸出格式（mask proto 維度、後處理在 CPU 的成本）

- Orin Nano 8GB 實測錨點：找 ≥2 個獨立來源的 s 級 TRT FP16 FPS（任何 YOLO 世代皆可，按 GFLOPs 比例外推 YOLO26）
- RAM 預算表：n@640（現役基線）/ n@1280 / s@640 / s@960 各自的 engine + workspace + activation 估算，對照 ≥0.8GB 餘量紀律
- 三條提升小物件 recall 路線的交叉比較：① 模型放大（n→s）② 輸入放大（640→960/1280）③ conf 0.5→0.3 + 時序確認（supervision spike）——哪條每 GFLOP 換到的 cup recall 最多
- seg 變體對「使用者想要輪廓」的真實成本：mask 後處理 Hz 影響、debug_image 疊 mask 的 CPU 成本、以及 mask 對顏色辨識的連動價值（goal 3 引用）
- D435 輸入端配套：目前餵 640x480，高解析模型要不要把 camera 拉到 1280x720（D435 RGB 支援）、letterbox 對 (1,300,6) 座標還原的影響

- 與 nav/brain 共存：object 6-8Hz 掉到多少以下會影響 S3 場景（cup 事件驅動，不需高 Hz——找出可接受下限）
